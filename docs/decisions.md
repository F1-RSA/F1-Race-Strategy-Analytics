### M1 · Docker base setup (2026-10-08)

- **Decision:** Two services on one user-defined bridge network (`f1_network`): `db` (PostgreSQL 16.10) and `ingestion` (Python 3.11.14, slim). The ingestion service waits for the database via `depends_on` with `condition: service_healthy`. Both images are pinned to exact versions. The database port is bound to `127.0.0.1` only. Configuration comes from `.env` (copied from `.env.example`, whose defaults work unchanged). The ingestion container is a placeholder (`sleep infinity`) until the ingestion package exists, so that `docker compose exec ingestion ...` works.
- **Alternatives:** `postgres:16` (floating tag) is not reproducible. Publishing the port on all interfaces exposes the database on the local network for no benefit. A one-shot ingestion container that exits was rejected because Kestra and the README both need to run commands inside a running container. Plain `depends_on` without a healthcheck only waits for the container to start, not for Postgres to accept connections.
- **Failure and rerun behaviour:** If Postgres is not healthy, the ingestion container is not started. The data lives in the named volume `pgdata` and survives `docker compose down`; `docker compose down -v` deletes it for a fresh start. Containers restart automatically unless stopped. Containers reach each other by service name (`db`) through Docker's DNS on `f1_network`; without a shared network the hostname `db` would not resolve.
- **Known limits:** The Postgres password in `.env.example` is a local-development value and must not be reused elsewhere. The init SQL (schemas and tables) is not part of this package (M3). A fixed `container_name` prevents running two copies of the stack on one host.

### M2 · HTTP layer and OpenF1 client (2026-10-19)

- **Decision:** One shared HTTP layer (`ingestion/f1_ingest/http.py`) and an OpenF1 client on top of it (`openf1.py`), configured only through environment variables (`config.py`, defaults in `.env.example`). The HTTP layer uses `httpx` (sync). A token bucket limits requests on the client side: capacity 2 (burst), refilled at 24 requests per minute, so any 60-second window contains at most 2 + 24 = 26 requests, below the 30/min we assume. Every attempt, retries included, takes a token. Retryable are 429, 5xx, timeouts and connection errors; between retries the client waits for `Retry-After` (seconds or HTTP date) if the server sends it, otherwise `uniform(0, min(60, 1 * 2^n))` seconds for retry n (exponential backoff with full jitter), at most 5 retries. Other 4xx fail immediately. The OpenF1 client fetches one request per endpoint and `session_key` (`sessions`, `drivers`, `laps`, `stints`, `pit`), never per driver or lap, and returns the JSON records unchanged so the original payload can go into JSONB. `fetch_session(session_key)` returns all five endpoints or raises. Clock, sleep, random source and transport are injectable, so tests run in milliseconds without network (`httpx.MockTransport`, sockets blocked in `conftest.py`) against responses recorded once from the live API for session 9472 (2024 Bahrain race; laps reduced to drivers 1 and 11, see `ingestion/tests/fixtures/openf1/README.md`). Verified live on 2026-10-19 with 9 requests: base URL `https://api.openf1.org/v1`, filter `?session_key=<n>`, an empty result is HTTP 404 with `{"detail":"No results found."}` (the same as for an unknown endpoint or an invalid filter value), no rate-limit or `Retry-After` headers, and `pit` returns `pit_duration` next to `lane_duration` and `stop_duration`.
- **Alternatives:** `requests` with urllib3's `Retry` hides the backoff and cannot use an injected clock, so timing and retries could not be tested deterministically; mocking it needs an extra library (`responses`). The standard library `urllib` has no dependencies but is awkward to mock. Async `httpx` gives no benefit at 24 requests per minute. Reacting to 429s only (no limiter) would hit the limit on every backfill. Fixed backoff without jitter makes parallel clients retry in lockstep. Fetching per driver would multiply requests by 20. Tests against the live API would be slow, flaky and depend on the rate limit; recorded fixtures make them repeatable and still use the real field names. Tests run on the host in a venv; installing the package in the image was deferred to M4 because nothing in the container uses it yet. `ingestion/.dockerignore` deliberately keeps the tests out of the image. Only direct dependencies are pinned (in `pyproject.toml`); a full lock file (`uv.lock` or pinned requirements) was rejected for now to keep the setup simple.
- **Failure and rerun behaviour:** On a 429 the client waits for `Retry-After` or the backoff, takes a new token and retries. After the last retry it raises `RetriesExhaustedError` with the last status; `fetch_session` then raises as well and returns nothing, so a session is never half-loaded through this client (M4 records the failure in `meta.load_log` and repeats the session on the next run). An empty result (404 "No results found.") becomes `[]`, any other 404 raises. Repeating a request is safe: all calls are GETs without side effects, so a rerun fetches the same records again and idempotency is left to the upsert in the database (M4).
- **Known limits:** The OpenF1 rate limit is not documented and not signalled, so 24/min is a conservative assumption (the plan says 30/min); it is configurable through `OPENF1_REQUESTS_PER_MINUTE` and `OPENF1_BURST`. The bucket is per process and not thread-safe; parallel runs would each have their own budget (Kestra concurrency limit 1, M7). `Retry-After` is honoured without an upper bound. A non-existent `session_key` returns `[]` just like a session without data; session keys must come from the `sessions` endpoint. `pit_duration` is deprecated in favour of `lane_duration`/`stop_duration`; the client keeps all fields and typing happens later. Access restrictions during live sessions and the rule to load only finished sessions (`date_end` in the past) are handled in M4. Transitive dependencies (httpcore, h11, certifi, …) are not pinned.
