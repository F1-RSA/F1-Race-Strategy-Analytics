## Entries

### M1 · Docker base setup (2026-10-08)

- **Decision:** Two services on one user-defined bridge network (`f1_network`): `db` (PostgreSQL 16.10) and `ingestion` (Python 3.11.14, slim). The ingestion service waits for the database via `depends_on` with `condition: service_healthy`. Both images are pinned to exact versions. The database port is bound to `127.0.0.1` only. Configuration comes from `.env` (copied from `.env.example`, whose defaults work unchanged). The ingestion container is a placeholder (`sleep infinity`) until the ingestion package exists, so that `docker compose exec ingestion ...` works.
- **Alternatives:** `postgres:16` (floating tag) is not reproducible. Publishing the port on all interfaces exposes the database on the local network for no benefit. A one-shot ingestion container that exits was rejected because Kestra and the README both need to run commands inside a running container. Plain `depends_on` without a healthcheck only waits for the container to start, not for Postgres to accept connections.
- **Failure and rerun behaviour:** If Postgres is not healthy, the ingestion container is not started. The data lives in the named volume `pgdata` and survives `docker compose down`; `docker compose down -v` deletes it for a fresh start. Containers restart automatically unless stopped. Containers reach each other by service name (`db`) through Docker's DNS on `f1_network`; without a shared network the hostname `db` would not resolve.
- **Known limits:** The Postgres password in `.env.example` is a local-development value and must not be reused elsewhere. The init SQL (schemas and tables) is not part of this package (M3). A fixed `container_name` prevents running two copies of the stack on one host.

### M3 · PostgreSQL schema (2026-10-15)

- **Decision:** The init scripts in `db/init/` (mounted read-only into `/docker-entrypoint-initdb.d`) create three schemas: `raw`, `core`, `meta`. Each raw table (`meetings`, `sessions`, `drivers`, `laps`, `stints`, `pit`) has the natural key from the OpenF1 API as primary key, `payload JSONB` with the original record, and `_ingested_at` / `_run_id`. `meta.load_log` records every load attempt per endpoint and session and is the basis for incremental loads. Keys and their reasons are in `docs/data_model.md`.
- **Alternatives:** Fully typed raw columns were rejected because an API change (such as the pit duration fields) would break the load; typing happens in `core`. A surrogate key per row was rejected because it cannot make upserts idempotent. For `raw.pit` the key `(session_key, driver_number, lap_number)` was rejected because a second pit lane entry on the same lap would be overwritten silently; the entry timestamp is used instead. A single status column on the session was rejected in favour of one log row per endpoint, because a session is only complete when all endpoints succeeded.
- **Failure and rerun behaviour:** The scripts use `IF NOT EXISTS` and run only on an empty volume; changing them later needs `docker compose down -v` (data is lost) or a manual migration. Reruns of a load upsert on the primary key and change no row counts. An interrupted load leaves `running` or `failed` rows in `meta.load_log` and is repeated on the next incremental run.
- **Known limits:** No Jolpica tables yet (M5), no `weather` or `race_control` (planned after the midterm). Without a foreign key, a lap can exist without its session row; load order is the responsibility of the ingestion. If OpenF1 corrects a pit timestamp, the old and new row both stay. No migration tool.
### M2 · HTTP layer and OpenF1 client (2026-10-19)

- **Decision:** One shared HTTP layer (`ingestion/f1_ingest/http.py`) and an OpenF1 client on top of it (`openf1.py`), configured only through environment variables (`config.py`, defaults in `.env.example`). The HTTP layer uses `httpx` (sync). A token bucket limits requests on the client side: capacity 2 (burst), refilled at 24 requests per minute, so any 60-second window contains at most 2 + 24 = 26 requests, below the 30/min we assume. Every attempt, retries included, takes a token. Retryable are 429, 5xx, timeouts and connection errors; between retries the client waits for `Retry-After` (seconds or HTTP date) if the server sends it, otherwise `uniform(0, min(60, 1 * 2^n))` seconds for retry n (exponential backoff with full jitter), at most 5 retries. Other 4xx fail immediately. The OpenF1 client fetches one request per endpoint and `session_key` (`sessions`, `drivers`, `laps`, `stints`, `pit`), never per driver or lap, and returns the JSON records unchanged so the original payload can go into JSONB. `fetch_session(session_key)` returns all five endpoints or raises. Clock, sleep, random source and transport are injectable, so tests run in milliseconds without network (`httpx.MockTransport`, sockets blocked in `conftest.py`) against responses recorded once from the live API for session 9472 (2024 Bahrain race; laps reduced to drivers 1 and 11, see `ingestion/tests/fixtures/openf1/README.md`). Verified live on 2026-10-19 with 9 requests: base URL `https://api.openf1.org/v1`, filter `?session_key=<n>`, an empty result is HTTP 404 with `{"detail":"No results found."}` (the same as for an unknown endpoint or an invalid filter value), no rate-limit or `Retry-After` headers, and `pit` returns `pit_duration` next to `lane_duration` and `stop_duration`.
- **Alternatives:** `requests` with urllib3's `Retry` hides the backoff and cannot use an injected clock, so timing and retries could not be tested deterministically; mocking it needs an extra library (`responses`). The standard library `urllib` has no dependencies but is awkward to mock. Async `httpx` gives no benefit at 24 requests per minute. Reacting to 429s only (no limiter) would hit the limit on every backfill. Fixed backoff without jitter makes parallel clients retry in lockstep. Fetching per driver would multiply requests by 20. Tests against the live API would be slow, flaky and depend on the rate limit; recorded fixtures make them repeatable and still use the real field names. Tests run on the host in a venv; installing the package in the image was deferred to M4 because nothing in the container uses it yet. `ingestion/.dockerignore` deliberately keeps the tests out of the image. Only direct dependencies are pinned (in `pyproject.toml`); a full lock file (`uv.lock` or pinned requirements) was rejected for now to keep the setup simple.
- **Failure and rerun behaviour:** On a 429 the client waits for `Retry-After` or the backoff, takes a new token and retries. After the last retry it raises `RetriesExhaustedError` with the last status; `fetch_session` then raises as well and returns nothing, so a session is never half-loaded through this client (M4 records the failure in `meta.load_log` and repeats the session on the next run). An empty result (404 "No results found.") becomes `[]`, any other 404 raises. Repeating a request is safe: all calls are GETs without side effects, so a rerun fetches the same records again and idempotency is left to the upsert in the database (M4).
- **Known limits:** The OpenF1 rate limit is not documented and not signalled, so 24/min is a conservative assumption (the plan says 30/min); it is configurable through `OPENF1_REQUESTS_PER_MINUTE` and `OPENF1_BURST`. The bucket is per process and not thread-safe; parallel runs would each have their own budget (Kestra concurrency limit 1, M7). `Retry-After` is honoured without an upper bound. A non-existent `session_key` returns `[]` just like a session without data; session keys must come from the `sessions` endpoint. `pit_duration` is deprecated in favour of `lane_duration`/`stop_duration`; the client keeps all fields and typing happens later. Access restrictions during live sessions and the rule to load only finished sessions (`date_end` in the past) are handled in M4. Transitive dependencies (httpcore, h11, certifi, …) are not pinned.

### M4 · Postgres sink and CLI (2026-10-21)

- **Decision:** `python -m f1_ingest.cli` loads OpenF1 sessions into `raw.*` and records every attempt in `meta.load_log`. The sink (`sinks/postgres.py`, psycopg 3) writes one endpoint of one session per transaction with `INSERT ... ON CONFLICT (primary key) DO UPDATE`: the key columns and `meeting_key` come from the record itself, the record is stored unchanged as `payload`, `_run_id` and `_ingested_at` are refreshed. A record without a key field, or two records with the same key in one response, raise an error before anything is written, so no row is skipped or merged silently. For each session the endpoints run in the order `sessions, drivers, laps, stints, pit`: a `running` log row is committed first, then the data is fetched, then rows and the `success` update are committed in one transaction. A session counts as loaded only if all five endpoints have a `success` row (`state.py`). **"New" is detected** as the sessions OpenF1 lists for the season minus the loaded ones (`--mode incremental`, default); `--mode full` reloads everything selected. Only finished sessions are loaded: `date_end` in the past (UTC, clock injectable), not cancelled. By default `session_type` = `Race`, which in OpenF1 contains the Sprint sessions (30 in 2024: 24 Race + 6 Sprint, checked live); other types can be added with `--session-type`. The session record needed for the selection is already fetched when the season is listed, so it is written from there: four requests per session instead of five. `--meeting-limit N` keeps the first N finished weekends and is applied before the "already loaded" filter, so the same command twice is a no-op and a larger N adds only the new weekends. Sessions are processed in date order. A failed session is logged and the others are still tried; the exit code is 1 if any failed (2 for invalid use, configuration or an unreachable database). `--target cloud` exists and stops with "not implemented yet (final milestone)". The Dockerfile now installs the package (direct dependencies pinned, `psycopg[binary]` brings its own libpq) and still idles so `docker compose exec` works.
- **Alternatives:** psycopg2 is older and needs `execute_values` and libpq in the image; SQLAlchemy adds an ORM layer for five statements. Fetching all five endpoints first and writing afterwards would hide which endpoint failed and keep 1100+ laps in memory for nothing; one log row per endpoint was already decided in M3. A single transaction per session was rejected: a failed `pit` request would discard the laps that loaded fine, and the log could not show where it stopped. Marking `success` in a second transaction after the data was rejected: a crash in between would leave data without the success row (harmless but confusing); in one transaction the success row proves the data is there. Treating `running` rows older than some timeout as dead was rejected as arbitrary; instead a `running` row never counts as loaded, and at the start of a run the `running` rows of earlier runs are set to `failed`. `--meeting-limit` as "the next N weekends" (limit after the incremental filter) was implemented first and rejected after the first live rerun: repeating the same command quietly loaded another weekend. The integration tests use a throwaway database `f1_test_<random>` on the compose server, so the unchanged `db/init` scripts are tested and `f1_db` is never touched; a test schema would need rewritten DDL, a rolled-back transaction conflicts with the per-endpoint commits.
- **Failure and rerun behaviour:** After the last retry the HTTP layer raises (a 429 is retried with `Retry-After` or backoff first, M2); the log row becomes `failed`, the session stays "not loaded" and the CLI exits with 1 after trying the remaining sessions. Endpoints that already succeeded stay committed, which is harmless because the next run writes them again. If the process is killed (checked live with `SIGKILL`, 6 seconds into session 9488): `sessions`, `drivers`, `laps` and `stints` were `success`, `pit` stayed `running`, the rows of those four endpoints were already in the tables, but 9488 was not in the loaded set. The next run set the stale row to `failed`, loaded 9488 completely (`pit` 36 rows) and the log kept both attempts. **A rerun is safe because every row has a natural key:** `(session_key)`, `(session_key, driver_number)`, `(session_key, driver_number, lap_number)`, `(session_key, driver_number, stint_number)`, `(session_key, driver_number, date)`. The same API record hits the same key and replaces the row, so row counts stay equal: loading session 9472 twice (once with `--mode full`) gave 1 / 20 / 1129 / 63 / 43 rows both times and no duplicate keys; only `_run_id` and `_ingested_at` changed. **If OpenF1 corrects data afterwards,** a full reload of that session overwrites `payload` for records with the same key. Incremental runs do not look at sessions that are already loaded, so a correction is picked up only by `--mode full`. **Pit key risk (see `data_model.md`):** the key uses the entry timestamp, so a corrected timestamp arrives as a second row instead of replacing the first; the old row stays until the table is rebuilt. This is visible by a query (two rows for one driver and lap), whereas the key with `lap_number` would lose a second pit lane entry on the same lap without a trace. If OpenF1 returns two pit records with the same timestamp the load fails loudly instead of merging them.
- **Known limits:** One run at a time is assumed (Kestra concurrency 1, M7): the start of a run closes all `running` rows of other runs, which would also close the rows of a run that is still working. A session whose latest full reload failed still counts as loaded because of its earlier `success` rows (each endpoint is atomic, but the session may mix old and new data). Records that OpenF1 deletes are not deleted here; upserts only add and overwrite. `date_end` in the past is our definition of "finished"; whether OpenF1 has finalised the data at that moment is not verified, `--mode full` repairs a session loaded too early. A session without data in an endpoint (for example no pit stops) is logged as `success` with 0 rows. Only Race and Sprint sessions are loaded by default; there is no `meetings` load yet. The rate limit of 24 requests per minute makes a whole season (30 sessions) take a few minutes. Transitive dependencies are still not pinned (see M2). The integration tests need the compose database and are skipped when it is unreachable, so CI (M8) has to start it.

### M5 · Jolpica client (2026-10-21)

- **Decision:** `JolpicaClient` (`jolpica.py`) fetches the schedule (`/<season>/races.json`) and all race results of a season (`/<season>/results.json`) through the shared HTTP layer, with its own base URL, a `User-Agent` and its own rate limit (`JOLPICA_*` variables, default 6 requests per minute, burst 2; Jolpica documents 4 per second and 500 per hour, "will decrease"). The load is per season, not per round: about 6 requests for a season (1 schedule + 5 pages of results) instead of 24 or more. **Pagination:** `limit` is capped at 100 and `MRData.total`, `limit` and `offset` count result ROWS, not races (all values are strings). A page border therefore falls inside a race (2024: rounds 6, 11, 16 and 21 start on one page and end on the next, checked live). The client advances the offset by the rows it received, merges a race that continues on the next page by `(season, round)` and returns every race once with its complete `Results`. It raises `PaginationError`, and nothing is loaded, if `total` changes between pages, a page has fewer or more rows than `min(MRData.limit, total - offset)`, a page is empty before `total` is reached, the offset is not the one asked for, the race data (everything except `Results`) differs between two parts of a race, or the structure is not the expected one. The server's `limit` is trusted, not ours, because the cap is echoed. **Tables:** `raw.jolpica_races` with key `(season, round)` and `raw.jolpica_results` with key `(season, round, driver_id)`, new init script `04_raw_jolpica.sql`. The result payload is the race object with `Results` cut down to one result, so it keeps the API shape and all values stay strings (`position`, `points`, `grid`, durations); typing happens in `core` (M6). The key uses Jolpica's `driverId`, not the position: a driver appears once per race (no duplicate `(round, driverId)` or `(round, position)` in the 1772 results of 2023 to 2026, checked 2026-10-21), whereas a position can change after a penalty, and a corrected position would arrive as a second row, like `raw.pit`. **Loading** (`jolpica_load.py`, `python -m f1_ingest.cli --source jolpica --season 2024`): write the whole schedule (one transaction, one `races:<season>` log row), then take the completed rounds (race date and time in the past, UTC, clock injectable; races without a time count from the next day), subtract those with a `success` row for `results:<season>:<round>` and fetch the season results only if rounds are left. Each round is written together with its `success` row in one transaction. A round that is over but has no published results is `pending`: it is not logged as loaded and a later run picks it up. `--mode full` rewrites all completed rounds. `meta.load_log` is used as it is: `source = 'jolpica'`, `session_key` NULL, the season and round in the `endpoint` text (`races:2024`, `results:2024`, `results:2024:7`); `LoadLog.succeeded_endpoints(prefix)` reads them. Verified live on 2026-10-21 against the compose database: 2024 gave 24 races and 479 results (the same as `MRData.total`), 20 per round and 19 in round 3, no duplicate keys, winners VER, VER, SAI, VER and VER 399 points as top of the table (the official 437 includes sprint points); the second run loaded nothing and made one request, `--mode full` kept 24 / 479; 2026 loaded the 17 completed rounds of 23 (374 results), the second run nothing.
- **Alternatives:** One request per round needs no pagination but about four times the requests (24 instead of 6 for a season), and Jolpica asks for fewer, larger requests. Asking with a very large `limit` does not work, the server caps it at 100. `(season, round, position)` as the result key was rejected (see above). A position-based offset or a race-based page count would lose or duplicate rows at the page borders; the tests with a page size of 25, 7, 20 and 1 and a mutation check (no merge, offset ignoring the rows received) show that they are caught. Nullable `season` and `round` columns in `meta.load_log` are cleaner than the endpoint text but change the M3 table and its documented watermark the day before the midterm; they are listed for the final milestone and need the team's agreement. Encoding the round into `session_key` was rejected as misleading. Subcommands or a second entry point instead of `--source` would change the existing OpenF1 call or duplicate connection, logging and exit codes. A User-Agent default with spaces and brackets broke `source .env`, so it is `f1-rsa-hslu-deng-hs26/1.0` without contact details (none are invented).
- **Failure and rerun behaviour:** The HTTP layer retries 429 (waiting for `Retry-After` if sent, else backoff), 5xx and timeouts, then raises; a throttled page is requested again, never skipped (test with `Retry-After: 7`). The client stays within 6 requests per minute (burst 2), so a season takes about 40 seconds; a real 429 was not provoked and its body and header are not verified. A failed schedule or results fetch (or a `PaginationError`) stops the run with exit code 1 and a `failed` log row; nothing of the results is written, and the schedule stays loaded. A failing round (for example two results with the same `driverId`) writes nothing, is logged `failed`, and the other rounds are still loaded; the next run loads exactly that round. A killed run leaves a `running` row that the next run sets to `failed`, as in M4. **A rerun is safe** because every row has a natural key and the writes are upserts: the second incremental run changes nothing, `--mode full` replaces the rows and leaves the counts the same, only `_run_id` and `_ingested_at` change. Jolpica results that are corrected afterwards (for example after a penalty) are picked up only by `--mode full`, because incremental runs skip loaded rounds. An empty answer is HTTP 200 with `total` 0; an unknown season therefore fails (`no races`) instead of loading nothing. Databases created before M5 do not have the tables (`db/init` runs only on an empty volume): `docker compose down -v && docker compose up -d --build`, which deletes the data.
- **Known limits:** Only races and race results are loaded; sprint results, qualifying, pit stops and standings are separate Jolpica endpoints (the points sum is lower than the championship, Verstappen 399 against 437 for 2024). There is no mapping between OpenF1 and Jolpica identifiers yet (`driverId` against `driver_number`, `round` against `meeting_key`); that is for the transformation (M6). Results are only as final as Jolpica's data on the day of the load. Completed means the race start is in the past: a round just after the start has no results yet and is `pending`, which is correct but not an error. Records deleted by Jolpica are not deleted here. The rate limit is a per-process assumption below the documented limits, and Jolpica announced that it will decrease; the values are configurable. The `meta.load_log` encoding in the `endpoint` text needs the `source` filter in every query that groups by `session_key`. Changes of the `total` while paging are detected and fail the run, they are not repaired inside it. The cloud sink and orchestration are not part of this package.

### M6 · Transformation: laps_enriched (2026-10-21)

- **Decision:** `core.laps_enriched` is a **view** with one row per lap of `raw.laps` and typed columns instead of JSON: `session_key, driver_number, lap_number, meeting_key, lap_duration_s, compound, stint_number, tyre_age_laps, is_pit_out_lap, has_lap_time`. **Why `/laps` has no compound:** OpenF1 records the tyre per stint (`/stints`: `compound`, `lap_start`, `lap_end`, `tyre_age_at_start`), not per lap, so the compound is found by joining the lap to the stint that covers it. `tyre_age_laps = tyre_age_at_start + (lap_number - lap_start)`. **What can go wrong in that join, checked on the 30 Race and Sprint sessions of 2024 (29,052 laps, 2,978 stints, read from the API on 2026-10-21):** (1) *Overlap:* a lap that two stints cover is returned twice by a plain `BETWEEN` join. This happens at pit stops: stint 1 ends on lap N and stint 2 starts on lap N; it is 100 laps in 2024, 36 of them in Australia alone, and in all 100 the boundary lap is shared exactly (never a wider overlap). (2) *Gap:* 61 laps (0.21 %) are covered by no stint, because 35 stints have NULL `lap_start`/`lap_end` and because of retirement laps. (3) *NULL:* 100 laps (0.34 %) have no `lap_duration` (51 of them lap 1); compounds include `UNKNOWN` (2 stints). `tyre_age_at_start` was never NULL in 2024. **Grain rule:** one row per `(session_key, driver_number, lap_number)`. `raw.laps LEFT JOIN LATERAL (stints of that driver that cover the lap ORDER BY stint_number LIMIT 1)`: a lap covered by several stints belongs to the **earliest** one, no `DISTINCT`. Reason: for all 36 overlaps in Australia the pit entry in `/pit` is on lap N and the out lap (`is_pit_out_lap`) is N + 1, so lap N is the in-lap, driven on the old tyres; the later stint's `lap_start = N` only marks where the new set was fitted. For the other 64 overlaps this is an assumption, not checked against `/pit`. A lap without a stint stays in the view (LEFT JOIN) with NULL compound, stint and tyre age; a stint without lap range matches nothing; nothing is guessed or interpolated. `compound` is kept as the API sends it (`UNKNOWN` stays `UNKNOWN`), `has_lap_time` is `lap_duration IS NOT NULL`. **Checks** (`transform.py`): *grain* = no lap key twice and as many rows as `raw.laps`; *coverage* = laps without stint, known compound, tyre age and lap time per session and in total. **CLI:** `python -m f1_ingest.cli --season 2024 --transform` runs after the load, `python -m f1_ingest.transform` runs alone; the SQL ships inside the package (`ingestion/f1_ingest/sql/`) so it is in the image and in every container that uses it, whatever the build context. **Verified live** with Bahrain, Saudi Arabia and Australia 2024 on a fresh database: 3029 rows in the view = 3029 in `raw.laps`, grain check passed, 0 laps with a stint but without compound or tyre age, 5 laps without stint (0.17 %: 0 / 2 / 3 per session), the plain join returns 36 laps twice in Australia and 0 elsewhere, and a second transform changes nothing (3029 laps, 3024 with compound, tyre age sum 37878). Example queries with their real results are in `docs/queries/`.
- **Alternatives:** A table instead of a view would read faster and is stored typed, but it can be stale after a load, needs a rebuild step and a truncate-and-insert transaction, and the data (about 30,000 laps per season) is too small to need it; the plan recommends the view and the final milestone replaces it by dbt anyway. `DISTINCT` or `GROUP BY` over the plain join would hide the duplicates without saying which stint a lap gets, and could return the wrong compound for the in-lap; `LIMIT 1` with an explicit order makes the rule visible. The *latest* stint would give the in-lap the new tyre, which contradicts the pit data. Choosing the stint by comparing with `/pit` or `is_pit_out_lap` was rejected as more code for the same result in the 2024 data. Guessing the lap range of stints with NULL `lap_start`/`lap_end` (from the neighbouring stints) was rejected: a wrong guess is worse than a visible gap. The SQL in `transformation/sql/` (the plan's tree) needs a volume or a repo-wide build context because the image is built from `./ingestion`; a volume does not exist in containers that Kestra starts. A `--transform-only` flag or subcommands would have changed the required `--season`/`--session-key` group of the existing CLI. Failing the run on poor coverage was rejected: a gap in OpenF1's stints is a data problem, and failing would block the weekly run and everything after it.
- **Failure and rerun behaviour:** The view holds no data, so the transform is `CREATE OR REPLACE VIEW` plus read-only checks: it can run after every load or alone, any number of times, and cannot leave half a result. It is also correct after a partly failed load (the view shows what is loaded; `--transform` runs even then). A failed grain check is logged as an error and the exit code is 1 (also for `python -m f1_ingest.transform`), a database error during the transform also gives 1, an unreachable database 2. By construction the grain cannot fail through the join (`LIMIT 1` per lap, `raw.laps` has the primary key); the check guards a future change of the SQL, and the tests prove it by running it on a deliberately wrong view (a plain join: duplicates; a view that drops a lap). Coverage is reported and warns above 2 % laps without stint in a session, but never changes the exit code.
- **Known limits:** Laps without a stint have no compound or tyre age (0.21 % in 2024); the share is reported per session. `lap_end` is taken as OpenF1 gives it; whether it is the in-lap or the last lap on the tyre differs between sessions (shared boundary lap in Australia, `lap_end + 1 = next lap_start` in Bahrain), and the rule above is verified only for Australia. **`tyre_age_laps` is therefore not on the same scale in both encodings:** with a shared boundary lap the out lap has age 1 (Australia, driver 27: stint 2 starts on lap 17 with age 0, out lap 18 has age 1), with `lap_start = N + 1` the out lap has age 0 (Bahrain). The difference is one lap for the first lap of each stint after the first; pace queries exclude out laps, so they start at age 1 in both cases. `tyre_age_at_start` comes from OpenF1 as is (used tyres start above 0); it was never NULL in 2024, a NULL gives a compound but no tyre age. The in-laps are slow and not marked in the view: the example queries remove them with `raw.pit`, other queries have to do the same. Lap times are not corrected for fuel load or traffic, so the averages by tyre age mix these effects (the SOFT band 00-09 is slower than 10-19 for this reason) and the degradation slopes are understated. Only OpenF1 data is used; there is no Jolpica join and no mapping of identifiers (M5 data stays in `raw`). The view is computed on every query; at this size that is fast, a larger volume would need a table or the dbt model. Only 2024 was checked for the data patterns; other seasons may have other gaps (2023 has 19 stints without lap range, no `UNKNOWN`).

### M7 · Kestra orchestration (2026-10-22)

- **Decision:** Kestra `kestra/kestra:v2.0.7` (standalone server, plugin-docker 1.8.0 inside the image) runs the flow `f1rsa.f1_weekly_ingestion` (`flows/f1_weekly_ingestion.yml`). Docs used: Kestra "Docker Compose" installation, "Server CLI" (`--flow-path`), "Flow concurrency" and the plugin schema of the running server (`/api/v1/plugins`, `/api/v1/main/flows/validate`); the syntax of v2 differs from older examples (see below). **Metadata:** a separate service `kestra_db` (postgres 16.10, own volume `kestra_pgdata`, own user and database), so that wiping or upgrading Kestra never touches `raw.*`, and the other way round. Kestra's repository and queue both use this Postgres, local storage uses the volume `kestra_data`. **Containers:** the flow starts one container per task with `io.kestra.plugin.docker.cli.Run` from the image `f1-ingestion:local` (compose builds it and names it; `pullPolicy: NEVER`, because it exists in no registry) with `networkMode: f1_network`. The compose network got the fixed name `f1_network` (without `name:` compose calls it `<project>_f1_network` and the flow could not name it). Containers find each other by service name through Docker's DNS on that network: the ingestion container reaches `db`, without the shared network `db` would not resolve. Database credentials reach the task as `{{ envs.postgres_* }}`, filled from environment variables `ENV_POSTGRES_*` that compose sets on the Kestra container from `.env`; the flow YAML contains no secret. **Auto-load:** `./flows` is mounted read-only at `/app/flows` and the server starts with `--flow-path /app/flows`; the flow is in the UI after `docker compose up` without a manual step (checked after a restart: revision 2 with the new tasks). Loading happens at startup only, so a change to the YAML needs `docker compose restart kestra`. **Inputs:** `season` (required), `session_key`, `mode` (incremental or full), `target` (local), `meeting_limit`, `include_jolpica`. A `session_key` wins over the season. **Tasks:** OpenF1 load, Jolpica load (`runIf`), then `f1_ingest.transform`. **Retry:** on the two load tasks, exponential backoff, 30 s start, at most 5 min, 3 attempts. **Concurrency:** `limit: 1`, `behavior: QUEUE`. **Schedule:** `0 6 * * 1`, UTC, input `season` = year of the trigger date, `mode` stays incremental. **UI and auth:** published on `127.0.0.1:8080` only, basic auth with local-development values from `.env.example`.
- **Alternatives:** *Cron plus the compose command* would also start the CLI on Mondays. What Kestra adds: a run history with the logs and inputs of every execution, retries per task with backoff, a queue instead of overlapping runs, a manual run with parameters (the backfill) and a visible failed state; with cron the cause of a failure lives in a mail or a log file nobody opens. *`docker compose exec ingestion ...` from Kestra* (a shell task inside the idle container) would need the Docker CLI and socket in Kestra anyway, and runs inside a shared long-lived container instead of a clean one per run. *Docker task runner on a shell task* is the other documented way; `docker.cli.Run` is shorter and is what the plan proposed. *Kestra on the F1 database* (one Postgres, two databases) saves a container but ties the lifecycle of orchestration state to the data and shares credentials. *Flow-level `pluginDefaults`* would remove the repeated `containerImage`/`networkMode`/`env` blocks, but Kestra v2 rejects the key in a flow (checked with the validate endpoint), so the three tasks repeat them. *YAML anchors* for the retry block were rejected by the parser too. Kestra's schedule *backfill* feature was not used: a manual run with `season` does the same for whole seasons and is simpler to explain. `latest` as image tag is not reproducible; the exact tag `v2.0.7` is pinned. The slim image (without plugins) was considered because the full image is about 4 GB, but it needs plugin downloads at startup.
- **Failure and rerun behaviour:** A non-zero exit code of the CLI fails the task (1 = a session or round failed or the grain check failed, 2 = invalid use or database unreachable). The task is then retried; after the third attempt the flow ends `FAILED` and later tasks are not run (checked with `season` = 1999, which OpenF1 has no data for: 3 attempts in about 96 s, flow `FAILED`, `transform` not started). A retry is safe because every write is an upsert on a natural key and loaded sessions are skipped (M4, M5), and the CLI sets stale `running` rows of earlier runs to `failed` at its start. **That is why concurrency is 1**: the cleanup would also close the rows of a run that is still working, and the rate limits (24 and 6 requests per minute) are per process. With `QUEUE` a Monday run that starts while a manual backfill is going waits instead of failing or being dropped. A rerun with the same inputs is green and changes nothing: verified on the live stack after `docker compose down -v && docker compose up -d --build` (all four services healthy, flow listed without a manual step): `season` = 2024, `meeting_limit` = 1 gave sessions 1, drivers 20, laps 1129, stints 63, pit 43, Jolpica races 24, Jolpica results 479, `core.laps_enriched` 1129, and exactly these counts again after an incremental rerun and after a `mode` = `full` rerun (`include_jolpica` off); `meta.load_log` gained rows only for the attempts. The backfill (`season` = 2023, `meeting_limit` = 1) added one weekend and the 22 rounds of 2023 (2 sessions, 40 drivers, 2187 laps, 133 stints, 43 pit rows, 46 races and 919 results in total; the 2023 weekend has no pit rows in OpenF1) and left the 2024 rows alone; its rerun changed nothing. A run that is killed in the middle (not tested with Kestra) leaves a `running` row that the next run closes, as in M4.
- **Known limits:** **Docker socket:** mounting `/var/run/docker.sock` into a container that runs as root gives that container the rights of the Docker daemon, in effect root on the host (it can start any container with any mount). It is the price for starting the ingestion containers from Kestra. Mitigations in place: nothing else is mounted from the host except the read-only `flows/`, the UI port is on `127.0.0.1`, the UI needs a login. Not done: a socket proxy that allows only container creation, or Docker-in-Docker, or rootless Docker; the basic-auth password is a known local default and must be changed for anything beyond a laptop. The metadata database port is not published. **Version drift in the syntax:** Kestra v2 names (`maxAttempts`, input type `BOOL`, no flow-level `pluginDefaults`, `io.kestra.plugin.docker.cli.Run`) differ from many online examples written for v0/v1; a newer image needs the flow re-validated (`POST /api/v1/main/flows/validate`). The server also logs "Auto-installed plugin artifacts [plugin-docker:LATEST]" at startup, which looks like a download of an unpinned plugin; the image already holds plugin-docker 1.8.0 and that is the version the flow ran with, but the message is not explained. The schedule uses the year of the trigger date, so the first Mondays of January load the new season (nothing to load yet) and the last races of the old season are caught by the run of the last Monday of December only if they finished by then. Python logs go to stderr, so Kestra shows the CLI's INFO lines with level ERROR. The first start pulls the 4 GB image. Kestra also loads its own `tutorial` example flows. There is no alerting on failure yet (the failed state is visible in the UI); the cloud target and the dbt step are added in the final milestone.

### M8 · Midterm wrap-up (2026-10-22)

- **Decision:** **CI** (`.github/workflows/ci.yml`, on every push and pull request, `ubuntu-24.04`, Python 3.11): install `./ingestion[dev]`, `ruff check`, `ruff format --check`, the offline tests (`pytest ingestion`) and the integration tests (`pytest ingestion -m integration`). The integration tests run against a `postgres:16.10` **service container** with the same user and password as `.env.example` (`f1` / `f1_local_dev`) and `POSTGRES_HOST=localhost`; they create their own throwaway database and apply the unchanged `db/init/*.sql` (`conftest.py`), so nothing else has to be prepared. The step fails if the report contains a skip (`-rs` and a grep), because a skipped integration test would mean that the database was not reachable and nothing was tested. Actions are pinned to exact tags (`actions/checkout@v4.2.2`, `actions/setup-python@v5.6.0`), the workflow has read-only permissions. **Architecture v0.2** (`docs/f1_pipeline_arch_v02.svg`, based on the style of v0.1, which stays in the repository) shows only what runs at the midterm; the cloud parts are dashed and grey. The table "Changes since v0.1" in the README has one row per real decision of M1 to M8, each with its package. **The guide:** the README starts with a quick path (clone, `.env`, `docker compose up -d --build`, one weekend with `--transform`, verification queries with their real numbers, rerun) that took 28 seconds from a clean state on a machine that already had the Kestra image, followed by the Kestra path (M7) and a Troubleshooting section whose entries are marked when we provoked them. Outdated "planned" texts, the test counts (now 137 offline and 71 integration tests, 28 files for ruff), the backlog and the known limitations were brought in line with the repository; the limitations are the "Known limits" of M2 to M7 grouped by topic. **Clean-clone test** (a copy of the working tree in a temporary directory, no `.env`, volumes removed first): `cp .env.example .env` works unchanged; `docker compose up -d --build` healthy after 18 seconds (warm cache); the flow is visible in Kestra without a manual step; one weekend loads in 8 seconds with the documented numbers (sessions 1, drivers 20, laps 1129, stints 63, pit 43, `core.laps_enriched` 1129, tyre age sum 10943); the rerun loads nothing and changes no count; a Kestra run (2024, one weekend) is green in 46 seconds and gives 24 Jolpica races and 479 results; lint and all 208 tests pass from a fresh venv. **One bug found and fixed:** with `POSTGRES_PORT=5433` in `.env` (the documented fix for a busy port) the ingestion container tried `db:5433` because `env_file` passed the host port into the container (`cannot connect to postgres at db:5433`, exit code 2). The `ingestion` service now sets `POSTGRES_HOST: db` and `POSTGRES_PORT: "5432"` itself; checked with 5433 and with `KESTRA_PORT=8081`.
- **Alternatives:** Starting the compose stack in CI (`docker compose up -d db`) would test the same file as locally, but needs the 4 GB Kestra image or a service filter and is slower; the service container is the same image and needs no compose. Running the integration tests only locally was rejected: the plan asks for CI, and the database tests are the ones that prove the upserts and the transform. A matrix of Python versions or operating systems was rejected for a project that pins 3.11 and one image. Pinning actions by commit SHA is stricter than tags, but the SHAs were not looked up and a wrong one breaks the workflow; tags are used and the SHA pinning is left for later. Redrawing v0.2 from scratch or editing the PNG of v0.1 was rejected: the SVG is generated in the same style so that the two versions compare directly. Dropping the cloud boxes would hide the plan; they stay, dashed. Putting the Kestra path first in the guide was rejected because the CLI path needs no 4 GB image and shows the data first.
- **Failure and rerun behaviour:** A failing lint, format check or test fails the workflow; a skipped integration test fails it too. The workflow has no side effects: the database is a service of the job and vanishes with it, and the tests drop their own database even when they fail. The guide can be run again at any time: steps 6 to 8 are idempotent (the second load loads nothing), and `docker compose down -v` returns to the start. If a step of the guide fails, Troubleshooting has the symptom as printed (ports, container names, Docker not running or disk full, unreachable API, an old database, flows that do not load).
- **Known limits:** The workflow has not run on GitHub yet when this entry is written (only `actionlint` and the same commands locally against PostgreSQL 16.10); the first run after the push is the real check. CI does not build the Docker image, does not start compose and does not validate the Kestra flow (a flow error shows up only when Kestra starts: `docker compose logs kestra`). The clean-clone test was one machine, macOS with Docker Desktop, with a warm image cache; the 4 GB pull, Linux, Windows and a second person are still to be checked by Florentin. The Troubleshooting entries for the Docker socket on Linux and Windows follow Docker's documentation and were not run. Actions are pinned by tag, not by SHA. The architecture diagram is a picture: it can drift from the code, and the table of changes is the part that is checked against the decision log.
